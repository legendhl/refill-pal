# 补货小管家（RefillPal）设计文档

- 日期：2026-09-25
- 状态：已与需求方确认（需求方确认了全部三段设计）
- 形态：微信小程序 + 微信云开发（CloudBase）

---

## 1. 背景与目标

管理家里的日用品：什么时候买了多少、大概能用多久、什么时候该补货。

一期目标：**自己家用，家人共享同一份数据，能收到微信推送提醒**。零服务器成本、零运维。

二期（不在本期范围）：上架、账号体系、多家庭、更多统计维度。

### 1.1 需求确认记录

| 议题 | 结论 |
| --- | --- |
| 使用范围 | 一期自己家用（家人共享数据 + 微信提醒）；二期考虑上架，账号体系延期 |
| 消耗估算 | 自动学习：记录购买历史，用历史消耗速度推算 |
| 录入方式 | 常用清单一键补货（宫格点一下即 +1） |
| 提醒策略 | 每日汇总推送一条 + 小程序内待补货页；引导续订订阅额度 |
| 记录字段 | 物品 + 数量 + 日期（必需）；金额；购买渠道；品牌/规格 |
| 一期功能 | 库存校准、消耗速度与预测展示、月度开支统计、购物清单分享到家庭群、家庭成员邀请与管理 |
| 开发环境 | 目前无 AppID / 云开发环境，先交付完整代码 + 部署文档，环境 ID 用占位符 |

### 1.2 平台硬约束（决定了架构）

1. **小程序不能后台本地推送**。只能使用「订阅消息」：用户每授权一次，才能推送一条；额度用完需再次进入小程序续订。长期订阅仅对政务民生、医疗等少数类目开放，家居工具类**申请不到**。
   → 因此提醒设计为「每日汇总一条」，与一次授权的额度正好匹配。
2. **小程序端直连数据库的默认权限是「仅创建者可读写」**。家人 A 写入的记录，家人 B 读不到。
   → 因此所有数据读写必须经过云函数（管理员权限），并在云函数内做归属校验。
3. **小程序关闭后代码不再运行**。
   → 因此定时检查必须由云开发的定时触发器唤醒云函数完成。

## 2. 核心概念与数据模型

### 2.1 概念

- **物品（Item）**：一个长期反复购买的东西，如「抽纸」。带单位（包/提/瓶）、分类、可选品牌与规格、可选冷启动估计（"大概能用 30 天"）。
- **流水（Event）**：构成物品完整时间轴的事件，只有三种类型：
  - `purchase`：购买。`+数量`，可带金额、渠道、品牌/规格。
  - `stocktake`：盘点。把库存**校准**为「还剩 N」。
  - `used_up`：用完。语义等价于盘点为 0，但它是**消耗周期的闭合信号**，对估算价值最高。

## 3. 消耗估算算法

设计目标：**准确、可解释、能如实告知置信度**。全部实现为 `cloudfunctions/_shared/core.js` 中的纯函数，便于单测。

### 3.1 库存结算：事件溯源 + 锚点法

> 实施期修正：原设计让 `items` 直接维护 `anchorAt/anchorQty` 快照，实测发现「写入时维护的累加值」与「由流水推算的事实」会不一致（撤销、补录、改错都会让两者分叉）。改为 **事件溯源**：`items` 只存不可变的初始基准 `baseAt/baseQty`，当前库存一律由流水重放得出。

不做逐日扣减（浮点误差会累积、且无法处理 rate 变化）。读取路径分三步：

1. **重放**：从基准点出发，按时间顺序对每条流水「先结算到该时刻，再作用流水」，得到 live item 的 `anchorAt + anchorQty`；
2. **结算**：`currentStock = anchorQty - rate * daysBetween(anchorAt, now)`；
3. **预测**：`剩余天数 = currentStock / rate`。

因为速率在区间内是常数，最终库存可化简为 `baseQty + Σ购买 − rate × 天数`（盘点会重置基线）。这保证了任意时刻的库存都能由流水唯一推导，不存在缓存与事实分叉。

### 3.2 速率估算：两段式

**冷启动**：仅当 `closedCycles === 0` 且用户填了 `initEstimateDays`：

```
rate = 首次购买数量 / initEstimateDays
```

**骨架 —— 补货间隔学习**：对同一物品的相邻 `purchase` 事件计算间隔天数与期间购买量，得到候选速率 `qty / gapDays`。

- 剔除异常值：`gapDays < 1` 视为补录，丢弃；
- 指数加权平均（EWMA），近期权重高：`rate ← α * sample + (1 - α) * rate`，`α = 0.4`；
- 至少 2 次购买才启用。

**校准 —— 盘点闭合**（权重高于骨架，因为它排除了「买了却没用」的干扰）：两次盘点/用完事件之间，`(上次剩余 + 期间购买量 − 本次剩余) / 间隔天数`。有任意一组闭合数据时，取闭合样本的加权平均，与骨架速率按样本数加权融合。

### 3.3 预测与提醒判定

```
预计用完日 = now + currentStock / rate
剩余天数   = currentStock / rate
```

触发补货的条件（满足其一）：

- `剩余天数 <= settings.remindDays`（默认 3 天）；
- `currentStock <= 0`（已用完或逾期）。

待补货列表按 `剩余天数` 升序；已逾期的置顶并标红。

### 3.4 已知取舍

- **速率按物品统算，规格仅作展示**。3 层抽纸与 2 层卷纸若是同一物品，混买会让速率失真。检测到用户中途变更规格时，UI 提示「规格变了，建议盘点一次」，用盘点数据校准。
- **置信度如实展示**，不假装精确：

| 闭合周期数 | 文案 |
| --- | --- |
| 0 | 估算中 |
| 1–2 | 粗略估计 |
| ≥ 3 | 较准 |

- 只有冷启动估计、从未盘点过的物品，UI 上标注「基于你的初始估计」。

## 4. 页面与交互

### 4.1 Tab 结构

**Tab 1 · 待补货（首页）**——打开就是答案

- 顶部「该买了」卡片区：按紧急度排序，显示物品名、「预计 2 天后用完」、当前库存；紧急用暖橙色，逾期未买标红。
- 中部「还够用」列表：按剩余天数升序。
- 右下角主按钮「记一笔」。

**Tab 2 · 物品**

- 全部物品按分类分组，带搜索；右上角新建物品。
- 详情页：库存 / 预计用完日 / 置信度 + 消耗速度曲线 + 购买历史时间轴 + 「盘点」「用完了」两个大按钮 + 编辑 / 归档。

**Tab 3 · 统计**

- 月度开支（含环比）、分类占比环图、消耗速度排行、日均花销。

**Tab 4 · 我的**

- 家庭成员与邀请、提醒设置（提前几天 / 每日汇总时间 / 免打扰）、分类管理、订阅额度续订、数据导出。

### 4.2 「记一笔」的 3 秒路径（最关键一屏）

点主按钮 → 底部弹半屏「常用物品」宫格（按最近 / 最频繁自动排序）→ 点一下即 +1，默认今天、数量 1 → 需要时就地展开金额 / 渠道输入 → 完成。

- 顶部 Toast「已记：抽纸 ×1」，**5 秒内可撤销**。
- 冷门物品走宫格内搜索框。
- 长按宫格项可快速改数量。

### 4.3 让家人愿意用的两个细节

- **购物清单分享**：待补货页一键生成清单海报 + 小程序卡片，转发到家庭群，家人点开看到同一份数据。
- **盘点极简**：详情页「还剩 ___」，默认填当前估算值，用户只改数字。

### 4.4 视觉与可用性

温暖居家风；主色暖橙 `#FF7A45`，辅色奶油白；卡片圆角 `16rpx`；主按钮高度 ≥ `88rpx`；正文 ≥ `28rpx`（照顾长辈视力）。空状态、加载态、错误态都要有明确文案，不用白屏。

## 5. 云端架构

### 5.1 云函数清单

| 云函数 | 职责 |
| --- | --- |
| `family` | 创建家庭、生成邀请码、加入、成员列表、移除 / 退出、更新提醒设置 |
| `item` | 物品 CRUD、盘点、用完、归档 |
| `purchase` | 记一笔、撤销、历史列表、常用物品排序 |
| `dashboard` | 首页一次聚合返回（待补货 + 还够用 + 概要） |
| `stats` | 月度 / 分类统计 |
| `notify` | 定时触发器：每日汇总推送 + 写 `pushLogs` |

**共享逻辑**：`cloudfunctions/_shared/core.js` 为唯一事实来源，由 `scripts/sync-shared.js` 复制到各云函数的 `shared/core.js`。**刻意不用 npm `file:` 依赖**，避免微信开发者工具上传时软链打包失败。

**统一入口约定**：每个云函数接收 `{ action, payload }`，返回 `{ ok, data }` 或 `{ ok: false, code, message }`。所有函数第一步做 `openid → familyId` 归属校验，校验不通过直接拒绝。

### 5.2 定时任务

`notify/config.json`：

```json
{
  "triggers": [
    { "name": "dailyRefillCheck", "type": "timer", "config": "0 0 9 * * * *" }
  ]
}
```

云开发 cron 为 7 位（秒 分 时 日 月 周 年），时区 UTC+8。

实施期修正：原计划定时器固定在 09:00、设置项「先做展示」。这会让用户设了 08:00 却收不到消息，
属于静默失败。改为 **cron `0 0 * * * * *`（每小时整点唤醒）**，只给「当前小时 == 家庭设定的推送时间」
的家庭推送，于是「每天几点推」是真的生效的。代价是每天多跑 23 次空转（只有几十毫秒、无数据库写入）。
同时把设置项限定为整点，`family/updateSettings` 会拒绝非整点，避免出现「设了 9:30 永远不推」。

### 5.3 订阅消息与额度管理

- `pushLogs` 的 `familyId + date` 唯一索引保证**幂等**，同一天绝不重复打扰。
- 一天一条汇总消息，与「一次授权 = 一条额度」精确匹配。
- 每次打开小程序时，若 `subQuota.remaining < 3`，引导一次续订授权（`wx.requestSubscribeMessage`），授权成功 `+1`。
- 推送成功 `-1`；返回 `43101`（用户拒收）→ 额度清零并标记 `blocked`，小程序内提示重新授权；
  返回 `47003`（模板参数不合法）→ 记为模板错误且**不扣用户额度**，因为这是配置问题不是用户的问题；
  额度为 0 → 跳过并写日志，便于排查「为什么没收到」。

实施期补充（上线后追加）：新增 `PUSH_ENABLED` 总开关，默认 **false** —— 申请模板需要等服务类目审核，
在那之前把整块推送功能收起来（首页续订卡、设置页的推送时间/预览/续订入口全部隐藏，云函数不发）。
「提前几天提醒我」保留，因为它决定的是 App 内「该买了」清单的时机，与推送无关。
开关放在客户端与云函数两处（两个运行环境读不到同一份配置），由 `scripts/check-json.js`
校验一致性 —— 只改一处会造成「界面说已打开、实际不发消息」，这是最难查的一类问题。

实施期补充：模板 ID 不需要在云函数里再配一份。用户在小程序点「续订提醒次数」时，
`family/subscribe` 会把模板 ID 顺手存进 `families.settings.templateId`，`notify` 从那里读。
少一处配置就少一处填错的机会。

### 5.4 并发与一致性

- 记一笔 / 盘点使用云开发**数据库事务**，同时写 `events` 与更新 `items` 锚点，避免半写。
- 并发增量用原子 `inc`，不读改写，避免家人同时记账丢笔。

## 6. 错误处理

| 场景 | 处理 |
| --- | --- |
| 无网 / 云函数失败 | 展示本地缓存的最近一次 dashboard，顶部标注「离线数据，可能不是最新」 |
| 重复点击 / 重复提交 | 前端按钮 loading 锁 + 幂等请求 ID |
| 撤销 | 前端 5 秒 pending 队列，撤销调 `purchase.delete` |
| 时间 | 一律取服务端时间；客户端只做展示，不参与计算 |
| 盘点值异常（剩余 > 历史总购买，或 > 上次盘点 + 期间购买） | 二次确认弹窗 |
| 越权（openid 不属于该 familyId） | 云函数直接拒绝并记录日志 |
| 订阅消息失败 | 按错误码分类：额度耗尽跳过、拒收停推、其他重试一次 |
| 首次使用（无家庭） | 引导创建家庭或输入邀请码加入 |

## 7. 测试策略

- **单元测试**（`node:test`，零依赖）：`_shared/core.js` 的纯逻辑
  - 速率估算：冷启动 / 单周期 / 多周期 / 异常值剔除 / 规格变更
  - 锚点结算：跨天、跨月、rate 变化前后
  - 待补货判定：提前天数边界、已用完、库存为 0
  - EWMA 权重：验证近期样本影响更大
- **真机验收清单**（写在 `docs/deploy.md` 附录）：记一笔、撤销、盘点、用完、邀请家人加入、双向数据可见、推送到达、额度耗尽、离线展示、越权访问被拒、异常盘点二次确认。

**环境占位符**：`miniprogram/config.js` 的 `ENV_ID`、`project.config.json` 的 `appid`、订阅消息 `templateId`，三处集中占位，填完即可运行。

**二期预留**：所有集合自带 `familyId`，代码不硬编码「单家庭」。二期加账号体系与多家庭时无需重构数据层。

## 9. 明确不做（YAGNI）

- 一句话自然语言录入、扫商品条码入库（一期用常用清单宫格）
- 长期订阅消息（平台不开放该类目）
- 微信服务号 / 短信 / 邮件提醒
- 比价、库存地点（放哪个柜子）、保质期管理
- 上架所需的账号体系、隐私协议、审核材料（二期）
